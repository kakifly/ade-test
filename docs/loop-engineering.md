# ループエンジニアリングの設計

このプロジェクトで、AIの作業を「作る → 検証する → 直す」のサイクルとして回すための仕組みの全体像です。人間が読むための文書で、AIが従う規則は `CLAUDE.md` に書かれています。

## 1. 考え方

- **検証できる基準を先に置く**: テスト、型チェック、画面の受入基準。成功・失敗が機械的に分かるものにする
- **失敗の内容をAIに返す**: 失敗したテスト名、期待値と実際の値を、そのままAIが読める形で返す
- **1回に1点だけ直す**: 何が効いたかを分かるようにする
- **止める条件を決める**: すべて成功したら終わり。同じ失敗が3回続いたら、方針を変えて、直らなければ人間に報告する
- **検証を回避させない**: テストの削除・スキップ・書き換えは、直し方として認めない

## 2. 検証の層

| 層 | タイミング | 内容 | 仕組み | 失敗したとき |
|---|---|---|---|---|
| 1 編集直後 | Edit・Write・MultiEdit のあと | 型チェック、単体テスト（約1秒） | PostToolUse hook（`.claude/hooks/hook-check.sh`） | 失敗内容がAIに返る（終了コード2） |
| 2 作業終了前 | AIが作業を終える直前 | 型チェック、テストDBの初期化、すべてのテスト | Stop hook（`.claude/hooks/stop-check.sh`） | 失敗するとAIは終えられず、直す。シェルで変更したファイルもここで検証される |
| 3 コミット前 | `git commit` の直前 | 型チェック、単体テスト | husky（`.husky/pre-commit`） | コミットが作られない |
| 4 PR・main | PRの作成・更新時、mainへのpush | 型チェック、テストDBの初期化、すべてのテスト（結合テストを含む） | GitHub Actions（`.github/workflows/ci.yml`） | PRのチェックが赤になる（ブランチ保護で必須にする） |
| 5 画面 | 機能の完成時 | 受入基準 A-01〜A-11 をブラウザで確認 | `/verify-ui`（Playwright） | NGを直して、該当の基準を再確認する |
| 6 最終 | 全タスクの完了後 | ブランチ全体を、新しい目で確認 | 別のエージェントによるレビュー | 指摘を1回の修正でまとめて直す |

`pnpm run verify` は、層2〜4で共通の「型チェック、テストDBの初期化、すべてのテスト」です。

## 3. 失敗の記録と歯止め

- **記録**: 層1・2の失敗は、`.claude/hooks/loop-record.sh` が `.claude/loop/failures.log`（git管理外）に追記する。失敗したテスト名の一覧から「署名」を作り、前回と同じ署名なら連続回数を増やす。違う失敗なら1に戻す。成功すると、解消の記録を残してリセットする
- **歯止め（層1）**: 同じ失敗が3回続くと、hookのメッセージに「直し方を変えて、直らなければ報告する」が加わる
- **歯止め（層2）**: 同じ失敗が3回続くと、Stop hookは作業の終了を止めない（無限に直させない）。AIはユーザーに報告する
- **手順の部品化**: `/fix-loop`（修復のループ）、`/verify-ui`（画面の確認）をスラッシュコマンドとして用意した

## 4. 抜け穴と限界

- 層1は、シェルのコマンドで書いたファイルを検証しない（層2が補う）
- hookはAIへの通知であり、編集の取り消しではない
- 層2は、変更がないターンでは動かない（会話だけのとき）。変更の有無は `dev`（`package.json` と `pnpm-lock.yaml` を含む）で見る
- CIが本当にマージを止めるには、GitHubのブランチ保護の設定が必要（リポジトリの設定であり、ファイルでは表せない）
- 結合テストは、共有のテストDB（`habit_app_test`）を初期化して使う。同時に2か所から実行すると衝突する
- テストが足りなければ、間違ったまま収束する。ループの質は、テストの質で決まる
