# 習慣チェックアプリ 設計書

## 意図と背景

シンプルなWebアプリ「今日の習慣チェック」を作る。アプリ自体が目的ではなく、作る過程で次の4つのエンジニアリングを体験することが主目的である。

- **プロンプトエンジニアリング**: AIへの指示の書き方で結果がどう変わるかを知る
- **コンテキストエンジニアリング**: AIに渡す情報（CLAUDE.md、設計メモなど）の選び方と置き場所を知る
- **ハーネスエンジニアリング**: テスト、hook、ブラウザ確認など、AIの作業を支え検証する仕組みを知る
- **ループエンジニアリング**: 「実装→検証→修正」のサイクルを回して品質を上げる流れを知る

アプリは小さくても、状態管理・日付ロジック・画面・API・DBを含むため、4つの体験の題材として適している。

## ゴール

- 習慣を登録・削除できる
- 今日の日付に対して、習慣ごとにチェックを付け外しできる
- 習慣ごとに連続達成日数（ストリーク）を表示する
- データはPostgreSQLに保存され、再読み込みしても残る
- 上記の挙動が自動テストで検証されている
- 4つのエンジニアリングそれぞれの体験が、作業の中で具体的な成果物（文書・設定・テスト・ログ）として残る

## 非ゴール

- ログイン・認証・複数ユーザー（単一ユーザー前提。Claudeの判断）
- 通知、グラフ、統計画面、カレンダー表示
- 過去日付の編集（今日分のみチェック可能）

## アンチゴール（技術的に動いても失敗とみなすもの）

- 4つの体験がどれか欠けた状態で完成扱いにすること
- 体験のためにアプリを過剰に作り込み、シンプルさを失うこと
- テストが通るだけで、実際の画面で動作確認していないこと
- 項目ごとのzodスキーマを画面・APIごとに重複定義すること（共有が崩れること）

## 技術構成（ユーザー指定）

- **言語**: TypeScript
- **パッケージ管理・バンドラ・テスト**: Bun（ワークスペースによるモノレポ。バンドルはBunのバンドラ、テストは `bun test`）
- **フロントエンド**: React + React Hook Form
- **バリデーション**: zod。**データ項目ごとにスキーマを定義し、各画面ではそれを組み合わせて画面のスキーマを定義する**
- **バックエンド**: NestJS
- **DB**: PostgreSQL
- **ORM**: Drizzle ORM。**DBのDDL（SQL）を正とし、`drizzle-kit pull` でスキーマ（TypeScriptのオブジェクト）を生成する**

- **UIデザイン**: 見た目は、リポジトリ直下の `DESIGN.md`（QuestUI デザインシステム）を参考にする。値はCSSのデザイントークンとして一箇所に定義する

## モノレポ構成

| パッケージ | 責務 |
|---|---|
| `dev/apps/web` | Reactの画面。React Hook Form + zodResolver。APIクライアント |
| `dev/apps/api` | NestJS。Drizzleでの永続化。DDLのSQLを管理 |
| `dev/packages/schemas` | **項目ごとのzodスキーマ**（習慣名、日付、ID など）と、その組み合わせによるAPI入出力・画面のスキーマ。web / api の両方が使う |
| `dev/packages/core` | ストリーク計算・日付処理の純粋関数（web / api の両方から使える） |

## 仕様の要点

- **項目スキーマ**: 習慣名・日付（`YYYY-MM-DD`）・IDなどを1項目1スキーマで `dev/packages/schemas` に置く。フォームのスキーマとAPIのリクエストスキーマは、これらを組み合わせて作る
- **ストリーク**: 今日から遡って、チェックが連続している日数。今日が未チェックの場合は、昨日までの連続日数を表示する（今日チェックすればその日数に+1される）。1日でも空けたら0に戻る。未来日付のデータは無視する
- **習慣名の検証**: 前後の空白を除去し、空は不可、同名の重複は不可。この検証はスキーマ（形式）とサービス（重複）に分けず、共通化の方針に従って一箇所で扱う
- **チェックの冪等性**: 同じ日付・同じ習慣へのチェック操作を繰り返しても結果が変わらない（DBは `(habit_id, date)` に一意制約）
- **日付**: 「今日」はクライアントの端末のローカル日付とし、チェック操作のたびに取り直してAPIに渡す。サーバーは、未来日付と過去日付（今日以外）のチェックを拒否する
- **削除**: 習慣を削除すると、そのチェック履歴も削除する。再登録した場合は新規扱い

## 実験の進め方（ユーザー承認済み）

- **完成の定義**: アプリ本体と、`docs/experience-log.md`（4つの体験を4章立てで記録）の両方が揃ったら完成
- **実験の組み込み方**: アプリは1回だけ作る。「曖昧な依頼 vs 明確な依頼」と「CLAUDE.mdあり vs なし」の比較は使い捨てのブランチで短く試し、結果だけをログに残す。ストリークをわざと不完全に作るループ実験は本線の中で行う
- **担当**: Claudeが実験を実行して記録し、ユーザーは結果を見て感想や判断を加える。プロンプトを書く場面ではユーザー自身にも書いてもらう

## 4つの体験の組み立て

1. **プロンプト**: 習慣名のバリデーション（項目スキーマ）を題材に、曖昧な依頼と成功条件つきの依頼を比べる
2. **コンテキスト**: CLAUDE.md（技術構成、スキーマ方針、`coding-guidelines` の3点、日本語ルール）の有無で、同じ依頼の結果がどう変わるか比べる
3. **ハーネス**: `bun test`、編集後にテストを走らせるClaude Codeのhook（PostToolUse）、型チェック、Playwrightでの画面確認
4. **ループ**: `dev/packages/core` のストリーク計算を最初は意図的に不完全に実装し、テスト失敗→修正→再実行のループで直す

## 設計時点での判断（Claudeの判断。変更可）

- **方針ルール**: CLAUDE.mdに書く方針は、ユーザーのスキル `coding-guidelines` の3点（冪等性の確保、条件分岐へのコメント付与、ロジック・特にvalidationの共通化）
- **壊れたデータ**: APIのレスポンスはzodで検証してからUIに渡す。検証に失敗したらエラー表示にする
- **hook**: Claude Codeのhook（PostToolUse）として `.claude/settings.json` に設定。gitのhookは使わない
- **DDLの管理**: SQLファイルを `dev/apps/api/db/ddl/` に連番で置き、それをDBに適用してから `drizzle-kit pull` でTypeScriptのスキーマを生成する。マイグレーション管理ツールは使わない
- **Bunのバージョン**: asdfに入っているBun 1.4.2を `.tool-versions` で固定する
- **NestJSの実行**: NestJSはBunで実行する。デコレータのメタデータなどで問題が出た場合は、ビルドをtscに切り替えることを検討する（Bun上での動作は最初のタスクで検証する）

## DBの用意（ユーザー決定）

- ユーザーが持つ既存のPostgreSQLを使う。Dockerは使わない
- 接続先は環境変数 `DATABASE_URL` で受け取る。接続情報（パスワードを含む）はリポジトリにコミットしない（`.env` は `.gitignore` に入れ、`.env.example` だけを置く）
- 開発用とテスト用でデータベースを分ける。テストはテーブルを作り直すため、既存データのあるデータベースには向けない（Claudeの判断）

## 未決事項（ユーザーに確認が必要）

- 既存PostgreSQLの接続先（ホスト・ポート・ユーザー）と、この環境（WSL）から到達できるか。開発用・テスト用のデータベースを新しく作ってよいか

## ビルダーに任せること

- ファイル構成と関数の分割（上記パッケージ境界の範囲内で）
- APIのエンドポイント設計（RESTで、習慣とチェックの2リソース程度）
- UIの見た目（シンプルで読みやすければよい）
- hookの具体的な設定内容
