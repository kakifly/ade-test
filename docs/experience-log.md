# 4つのエンジニアリング体験ログ

この文書は、習慣チェックアプリの開発を通じて体験した、プロンプト／コンテキスト／ハーネス／ループの各エンジニアリングの記録です。

## 1. プロンプトエンジニアリング

- **やったこと**: 題材は習慣名の項目スキーマ `habitNameField`。同じ目的の依頼を2通りの書き方で、文脈を持たない新しいサブエージェントに実行させた（使い捨てのworktreeとブランチ。本線にはマージしない）。
  - 曖昧な依頼（ユーザーの言葉）:「入力チェックを作って」 → `experiment/prompt-vague`（`03b4fa2`）
  - 明確な依頼: ユーザーの1文「入力は文字列です。出力は、前後の空白を除去した文字列です。50文字以内です。」に、Claudeが、ファイルと関数名、拒否・許可の条件、テストを先に書くこと、スコープの限定、完了条件を足した → `experiment/prompt-clear`（`a6d5f66`）
- **結果**（ブランチは削除せず残してある）:

| 観点 | 曖昧な依頼 | 明確な依頼 |
|---|---|---|
| 変更の規模 | 10ファイル、162行 | 4ファイル、48行 |
| 作ったもの | 習慣名のほか、ID・日付・連続日数・行バージョン・作成日時の項目、画面・API用の組み合わせスキーマ7種 | `habitNameField` だけ |
| 拒否条件の網羅 | 空、空白のみ、51文字（テストあり） | 空、空白のみ（全角空白を含む）、除去後51文字以上（テストあり） |
| 境界値（50文字は可） | 50／51文字をテスト | 50文字（前後に空白付き）をテスト |
| テストを先に書いたか | 不明（報告なし） | 実装前に失敗（モジュールなし）を確認 |
| 余計な変更 | 依頼外の項目スキーマを多数追加 | `zod` の依存追加のみ（`package.json`、`bun.lock`）。報告でも触れた |
| 解釈の確認 | 「入力チェック」を基本設計のバリデーション設計章全体と解釈し、確認なしに進めた | 解釈の余地なし |
| テスト・型チェック | 22件成功、型チェック成功 | 16件成功、型チェック成功 |
| 手戻り | 範囲を絞る修正が必要（レビューの手間が増える） | なし |

- **気づき**:
  - 曖昧な依頼でも、プロジェクトの `CLAUDE.md` と設計書を自動で読むため、大きくは外れなかった。ただし「どこまで作るか」は依頼側が決めないと、AIが広く解釈する。
  - 「入力チェック」だけでは、対象（習慣名だけか、全項目か）、範囲（スキーマだけか、画面・APIも含むか）、完了条件が決まらない。AIはこれを確認せず、自分の解釈で埋めた。
  - 明確な依頼で効いたのは、(1) 対象を1つの関数に絞る、(2) 拒否と許可の例（境界値）を挙げる、(3) 「作らないもの」を書く、(4) 完了条件をコマンドで書く、の4点。
  - ユーザー自身の1文（入力・出力・上限）が、依頼の核になった。ただし「除去後に数える」といった曖昧さは、Claudeが条件として補った。
  - 前提の限界: サブエージェントは `CLAUDE.md` を読めたため、「文脈なし」の比較にはなっていない。文脈の効果は第2章で別に確認する。
- **ユーザーの感想**: どこまで作成するかを、ユーザーが指示する必要があることがわかった。

## 2. コンテキストエンジニアリング

- **やったこと**: （実装前に、`CLAUDE.md`、`SPEC.md`、`TASK.md`、`docs/ai-input/`、`DESIGN.md` を整えた。資料を「AIが読む正本」「顧客提出用」「人間の閲覧用」に分けた）
  - 比較: 同じ依頼「習慣を追加するフォームのスキーマを作って」を、AIに渡す資料だけ変えて実行した。実行は、リポジトリ外に作ったworktreeで `claude -p`（新しいセッション）を使い、上位ディレクトリの `CLAUDE.md` が混ざらないようにした。
    - 文脈なし: `CLAUDE.md`、`SPEC.md`、`TASK.md`、`DESIGN.md`、`docs/` を削除したもの → `experiment/context-none`（`8864785`）
    - 文脈あり: 今のリポジトリのまま → `experiment/context-full`（`07f1341`）
- **結果**（ブランチは残してある。本線にはマージしない）:

| 観点 | 文脈なし | 文脈あり |
|---|---|---|
| 習慣の項目 | 習慣名・説明（200文字）・実施頻度（毎日／曜日指定）の3項目 | 習慣名のみ |
| 習慣名の上限 | 50文字（仮に決めた） | 50文字（設計書どおり） |
| 項目スキーマの分け方 | 画面用スキーマ1つにまとめて定義（`habit-form.ts`） | `habitNameField` を `fields/` に分け、フォーム用・リクエスト用スキーマがそれを参照 |
| 配置先 | `src/packages/schemas/src/` 直下 | 設計書どおり `fields/` と `create-habit.ts` |
| 名前 | `addHabitFormSchema` | `createHabitFormSchema`、`createHabitRequestSchema`（設計書の名前） |
| 余計な機能 | 説明・実施頻度（設計にない項目） | なし |
| 判断の根拠 | 「仕様が見当たらないので仮に決めた」と報告 | `docs/ai-input/basic-design.md` の2章に沿った |
| 変更の規模 | 5ファイル、95行 | 6ファイル、81行 |
| テスト・型チェック | 16件成功、型チェック成功 | 18件成功、型チェック成功 |

- **気づき**:
  - 文脈なしでは、AIは足りない仕様を自分で作り、設計にない項目（説明、実施頻度）まで足した。ただし「仮に決めた」と正直に報告しており、確認を求める形ではあった。
  - 文脈ありでは、設計書にある名前、配置先、項目スキーマの分け方、上限をそのまま使った（報告では、根拠として `basic-design.md` を挙げていた）。
  - 文脈の価値は、AIの能力を上げることではなく、AIが推測で埋めていた部分を減らすことにある。
  - 資料は「何を作るか」（SPEC・ai-input）、「どう作るか」（CLAUDE.md）、「見た目」（DESIGN.md）に分けて置いたので、AIが必要な資料に当たりやすかった。
  - 前提の限界: ユーザー全体の `~/.claude/CLAUDE.md`（日本語で書く、など）は両方の条件で読まれる。また、文脈ありの側だけがテストを先に書いたが、これが `CLAUDE.md` の効果か、使っているスキルの効果かは、この実験では切り分けていない。
  - 文脈なしの側は、実験用に資料を消した状態で動かしたため、現実の「資料のないプロジェクト」より厳しい条件になっている。
- **ユーザーの感想**: 文脈を指定することで、AIの推測が減ることがわかった。
